# job-api

작업(Job)을 만들고 조회하고 수정하는 REST API 와, 대기 중인 작업을 주기적으로 집어가
처리하는 백그라운드 처리기입니다. 데이터는 JSON 파일 하나(`jobs.json`)에 저장하고,
모든 HTTP 요청과 처리 결과는 `logs.txt` 에 남깁니다.

NestJS 12 · TypeScript 6 · node-json-db · @nestjs/schedule · vitest

핵심은 [동시 접근](#동시-접근)과 [한계](#한계)입니다.

## 실행

Node 22 이상.

```bash
npm install
npm start          # http://localhost:3000
npm test           # 단위
npm run test:e2e   # HTTP 요청을 실제로 보내는 통합 테스트 (동시성 검증 포함)
```

`jobs.json` 에 표본 7건이 있어 바로 조회됩니다. 띄워 두면 10초마다 처리기가 `pending`
작업을 처리하고 `logs.txt` 가 한 줄씩 쌓입니다. 표본 중 하나(`Rebuild search index`)는
처리 도중 중단된 모습으로 두었습니다 — 첫 실행에 `job.recovered` 가 찍히고 다시 처리됩니다.
실행하면 처리기가 `jobs.json` 을 고치므로 `git status` 가 더러워집니다. `git checkout jobs.json` 으로 되돌립니다.

설정은 전부 환경변수이고 기본값으로 동작합니다.

| 변수                                          | 기본값                                |                                                  |
| --------------------------------------------- | ------------------------------------- | ------------------------------------------------ |
| `PORT` · `JOBS_DB_PATH` · `LOG_FILE_PATH`     | `3000` · `./jobs.json` · `./logs.txt` |                                                  |
| `SCHEDULER_ENABLED` · `SCHEDULER_INTERVAL_MS` | `true` · `10000`                      | 실행해 보는 사람이 오래 기다리지 않게 짧게       |
| `SCHEDULER_BATCH_SIZE`                        | `5`                                   | 한 주기에 집어갈 최대 건수                       |
| `STALE_PROCESSING_MS`                         | `60000`                               | 이보다 오래 `processing` 이면 중단으로 보고 회수 |
| `JOB_FAILURE_RATE` · `JOB_WORK_DURATION_MS`   | `0.2` · `50`                          | 처리 로직 대신 넣은 확률적 실패와 지연           |

없으면 기본값을 쓰지만 **있는데 틀리면 기동하지 않습니다** (`SCHEDULER_BATCH_SIZE=abc` →
즉시 실패). 조용히 기본값으로 대체하면 운영자는 자기 설정이 반영됐다고 믿게 됩니다.

## 데이터 모델

```jsonc
{
  "id": "uuid",
  "title": "…",
  "description": "…",
  "status": "pending", // pending | processing | completed | failed
  "version": 1, // 쓰기마다 +1. 낙관적 동시성 제어용
  "attempts": 0, // 처리기가 집어간 횟수
  "createdAt": "…",
  "updatedAt": "…",
  "startedAt": null,
  "finishedAt": null,
  "result": null,
  "error": null,
}
```

파일 최상위는 `{ "jobs": [...], "idempotency": {...} }`.

```
                 ┌──────────────────────────────┐
                 │      중단 감지 후 회수         │
                 ▼                              │
 (생성) ──▶  pending  ──────▶  processing  ──────┤
                 ▲                              ├──▶  completed   (종착)
                 │                              └──▶  failed
                 └──────────────────────────────────────┘
                          클라이언트가 재투입
```

- `pending → processing → completed | failed` 는 처리기가 일으킵니다.
- **자동 재시도는 없습니다.** 재시도는 어떤 실패가 재시도할 가치가 있는지 분류하는 것이
  전제인데, 여기 처리는 흉내라 분류할 근거가 없습니다. 모르는 채 반복하면 외부 부작용이
  중복됩니다. 다시 돌릴지는 `PATCH {"status":"pending"}` 으로 클라이언트가 정합니다.
- 클라이언트가 직접 일으킬 수 있는 전이는 `failed → pending` 뿐입니다. 나머지는 `409`.
- `title`·`description` 은 `pending`·`failed` 에서만 고칠 수 있습니다. 실행 중인 작업의
  입력을 바꾸면 결과가 무엇에 대한 것인지 흐려지고, 끝난 작업은 "무엇을 처리했는가"가
  사후에 달라집니다. 시도하면 `409`.

## API

단건은 작업 객체 그대로, 목록은 `{ data, meta }`. DTO 에 없는 필드가 오면 `400` —
오타 난 필드가 조용히 무시되는 쪽이 더 나쁩니다.

**`POST /jobs`** — `201` + `Location` + `ETag: "1"`. `title` 1~200자 필수, `description` 선택.

```bash
curl -X POST localhost:3000/jobs -H 'Content-Type: application/json' \
  -d '{"title": "Send welcome email", "description": "신규 가입자 대상"}'
```

```json
{
  "id": "7a4b1c08-5b0f-4d92-934b-b48b0ca823fc",
  "title": "Send welcome email",
  "description": "신규 가입자 대상",
  "status": "pending",
  "version": 1,
  "attempts": 0,
  "createdAt": "2026-09-24T03:15:48.232Z",
  "updatedAt": "2026-09-24T03:15:48.232Z",
  "startedAt": null,
  "finishedAt": null,
  "result": null,
  "error": null
}
```

`Idempotency-Key` 헤더를 주면 같은 키의 재요청은 처음 만든 작업을 그대로 돌려줍니다
(`Idempotent-Replay: true`). 같은 키에 다른 본문이면 `409`. 키 조회와 생성이 같은 임계
구역 안에 있어야 합니다 — 따로 하면 동시에 온 두 요청이 둘 다 "아직 없다"를 읽고 둘 다
만듭니다. 키는 128자까지(초과 `400`), 인증이 없어 범위는 전역, 파일에 영구 저장(만료 없음).

**`GET /jobs`** — `?page=1&limit=20`, 최신순, `limit` 상한 100. 생성 시각이 같으면 id 로
순서를 확정합니다 — 흔들리면 페이지 경계에서 항목이 겹치거나 빠집니다.

```json
{ "data": [ … ], "meta": { "total": 7, "page": 1, "limit": 20, "totalPages": 1 } }
```

**`GET /jobs/search`** — `?title=send&status=pending,failed`. `title` 은 부분 일치(대소문자
무시), `status` 는 쉼표 또는 반복 파라미터로 여러 개, 둘 다 주면 둘 다 만족. 이 라우트는
`GET /jobs/:id` 보다 먼저 선언해야 합니다 — 뒤집히면 `search` 가 id 로 잡힙니다. 순서에만
기대지 않도록 `:id` 에 UUID 검증도 걸었고, 뒤집히면 깨지는 테스트가 있습니다.

**`GET /jobs/:id`** — `ETag: "<version>"`. UUID 가 아니면 `400`, 없으면 `404`.

**`PATCH /jobs/:id`** — 바꿀 수 있는 건 `title`, `description`, `status`. 나머지는 서버
소유이고 보내면 `400`. 빈 본문이나 **결과가 지금과 같은 요청**(현재 상태를 다시 보내는 것,
같은 제목을 다시 보내는 것)도 `400` — 아무것도 안 바꾸면서 버전만 올리고 `ETag` 를 무효화하는
것을 막습니다. `null` 은 생략이 아니라 잘못된 값입니다(`400`).

```bash
curl -X PATCH localhost:3000/jobs/<id> -H 'Content-Type: application/json' \
  -H 'If-Match: "3"' -d '{"title": "v2"}'
```

`200` 과 바뀐 작업 객체(`POST` 응답과 같은 모양, `version` 이 하나 오른 값). 응답 헤더 `ETag` 도 새 값입니다.

`If-Match` 는 선택입니다. 주면 읽은 시점의 버전과 비교해 어긋나면 `412`, 안 주면 마지막
쓰기가 이깁니다. 필수로 하고 없으면 `428` 을 주는 쪽도 검토했는데, 그러면 `failed → pending`
재투입 같은 단순 조작까지 `GET` 을 먼저 거쳐야 합니다. 동시 수정이 문제가 되는 것은 사람이
화면에서 고치는 경우고 그 클라이언트는 `If-Match` 를 붙이면 됩니다. 운영에서 마지막 쓰기가
이기는 것이 문제가 되면 `428` 로 바꾸는 것은 한 줄입니다.

**오류 응답** — 프레임워크의 `404`, 검증 `400`, 도메인 오류, 예상 못 한 예외가 전부 같은
모양입니다. 분기는 `message` 가 아니라 `code` 로.

```json
{
  "statusCode": 409,
  "code": "INVALID_STATUS_TRANSITION",
  "message": "Cannot change status from 'pending' to 'completed'.",
  "details": { "from": "pending", "to": "completed", "allowed": [] },
  "path": "/jobs/…",
  "requestId": "…",
  "timestamp": "…"
}
```

| 코드 | `code`                                                                         |
| ---- | ------------------------------------------------------------------------------ |
| 400  | `VALIDATION_FAILED` `BAD_REQUEST` `EMPTY_UPDATE` `IDEMPOTENCY_KEY_INVALID`     |
| 404  | `JOB_NOT_FOUND`                                                                |
| 409  | `INVALID_STATUS_TRANSITION` `CONTENT_NOT_EDITABLE` `IDEMPOTENCY_KEY_REUSED`    |
| 412  | `VERSION_CONFLICT` — `If-Match` 실패는 RFC 9110 상 409 가 아니라 412           |
| 413  | `PAYLOAD_TOO_LARGE` — 본문 100 KB 초과. Express 가 던지는 오류도 같은 모양으로 |

`requestId` 는 응답 헤더 `X-Request-Id` 와 같고 `logs.txt` 에도 남습니다.

## 동시 접근

**먼저 확인한 것.** `node-json-db` 가 동시 쓰기에 안전하지 않다고 전제하고 시작했는데,
2.6.0 소스를 읽어 보니 `getData` 는 읽기 잠금, `push`/`delete` 는 쓰기 잠금을 이미 잡습니다.
호출 하나하나는 직렬화되어 있습니다. 문제는 작업 하나를 고치려면 `getData()` → 수정 →
`push()` 로 호출이 두 번이고 잠금은 각 호출 안에서만 유지된다는 것입니다. 두 요청이 모두
읽기를 먼저 끝내면 같은 낡은 배열을 들고 있게 되고, 나중에 쓰는 쪽이 앞선 변경을 덮어씁니다.
막아야 할 것은 라이브러리의 결함이 아니라 **라이브러리의 임계 구역이 내가 필요한 범위보다
좁다**는 것입니다.

**왜 잠금인가.** 저장소가 조건부 쓰기(없을 때만 넣기, 이 버전일 때만 고치기)를 지원하면
잠금 없이 저장소 자체를 경계로 삼아 같은 요청을 같은 레코드로 수렴시킬 수 있습니다.
가능하면 그쪽이 낫습니다. 이 저장소에는 그게 없고, 파일 하나를 통째로 읽고 쓰는 구조라
"확인하고 없으면 넣기"를 원자적으로 만들 방법이 직렬화뿐입니다. 뮤텍스는 첫 번째 선택이
아니라 저장소 제약에서 나온 선택이고, 저장소를 바꾸면 제일 먼저 걷어낼 것입니다.

**어떻게 막았나.**

1. 데이터 파일에 닿는 곳은 `JobsRepository` 뿐이고, 변경은 전부 `mutate()` 를 거쳐
   읽고-고치고-쓰기가 한 임계 구역 안에서 끝납니다. 직렬화는 `src/common/mutex.ts` 의
   작은 FIFO 뮤텍스가 합니다. `async-mutex` 로 대체할 수 있고 실무라면 그랬을 텐데,
   핵심 장치라 동작을 드러내 뒀습니다. 잠금 순서는 항상 내 뮤텍스 → node-json-db 잠금
   한 방향이라 교착은 없습니다.
2. 뮤텍스는 이 프로세스 안의 동시 쓰기만 줄 세웁니다. 클라이언트가 `GET` 으로 읽고 사람이
   화면에서 고치고 `PATCH` 하는 사이는 잠금으로 못 막습니다 — 막으려면 화면을 여는 동안
   잠금을 쥐어야 합니다. 그 구간은 `version` + `ETag`/`If-Match` 로. 다른 두 문제라 장치도
   둘입니다.
3. `getData` 는 내부 객체의 참조를 그대로 돌려줍니다. `data.jobs.push(x)` 하면 저장한 적
   없는 `x` 가 다음 읽기에 보입니다(직접 확인). 저장소 경계에서 `structuredClone` 으로
   끊었습니다.
4. 읽기에는 잠금을 걸지 않았습니다. `mutate()` 는 완성된 상태를 한 번에 써 넣고 단일
   스레드라 반쯤 쓰인 상태가 읽히지 않습니다.

**처리기는 잠금을 짧게 잡습니다.** 한 주기는 집어가기(잠금 안: `pending → processing` 저장)
→ 처리(잠금 밖) → 마무리(잠금 안: `completed`/`failed`) 입니다. 처리가 오래 걸리는 동안
잠금을 쥐면 모든 API 요청이 같이 멈춥니다.

- 중복 처리를 막는 것은 집어가기입니다. 임계 구역 안에서 `processing` 으로 바꾸므로 다른
  주기가 겹쳐 와도 같은 작업을 다시 집어갈 수 없습니다. 중단 회수와 집어가기를 같은 임계
  구역에서 하는 것도 같은 이유입니다.
- 주기가 겹치면 건너뛰는 `running` 표시는 중복 방지가 아니라 동시 실행 수를 하나로
  제한하는 장치입니다. 처리가 주기보다 오래 걸리면 실행이 쌓여 각각 배치 크기만큼 집어가고,
  배치 크기가 "한 번에 이만큼"이라는 뜻을 잃습니다. 처음엔 "겹침이 중복의 원인"이라고
  적었는데 집어가기가 원자적인 이상 틀린 설명이었습니다.
- 마무리 때는 상태가 `processing` 인지에 더해 집어갈 때의 `attempts` 와 같은지 확인합니다.
  처리하는 동안 방치로 회수되고 다른 실행이 다시 집어갔다면 상태는 여전히 `processing`
  이지만 남의 실행입니다. 회수를 넣은 이상 이 확인이 짝으로 따라와야 합니다. 지금은 실행이
  겹치지 않아 실제로 일어나진 않지만, 프로세스가 둘이 되는 순간 필요해집니다.

**검증.** 동시에 요청을 던지고 디스크 파일을 직접 읽어 확인합니다. 그리고 같은 워크로드를
**실제 뮤텍스를 끈 채로** 한 번 더 돌려 그때는 깨지는지 봅니다. 끄고도 통과하면 경합이 안
일어난 것이고 그 테스트는 아무것도 증명하지 못합니다. (`test/concurrency.e2e-spec.ts`)

| 워크로드                             | 뮤텍스 켬                      | 뮤텍스 끔    |
| ------------------------------------ | ------------------------------ | ------------ |
| 동시 생성 100건                      | 100건 전부 남음                | 유실         |
| 동시 수정 50건                       | `version` 이 정확히 51         | 51 미만      |
| 같은 멱등 키 25건 (서비스 직접 호출) | 작업 1건                       | 여러 건 생성 |
| 처리기 3회 + 요청 40건               | 유실 없음, 두 번 집어가지 않음 | 유실         |

멱등 키 줄만 HTTP 가 아니라 서비스를 직접 부릅니다. 처음엔 HTTP 로 던졌는데 뮤텍스를 꺼도
통과했습니다(5회 모두, 매번 정확히 한 요청만 "키 없음"을 봤습니다). 같은 HTTP 경로의 동시
생성은 깨지는데 이것만 통과하는 이유는 확정하지 못했습니다. 서비스를 같은 틱에서 25번
부르면 뮤텍스 없이 25건이 전부 새로 만들어지는 것은 확인했고, 그래서 표에는 이쪽을 넣었습니다.

114건(단위 36 + 통합 78) 통과.

## 로깅

`logs.txt` 에 한 줄 = 한 JSON. 이벤트명은 `대상.동사`(`job.claimed`, `scheduler.tick`).

```jsonc
{"timestamp":"…","channel":"http","event":"request.finished","requestId":"…","method":"POST","path":"/jobs","statusCode":201,"durationMs":3.6}
{"timestamp":"…","channel":"scheduler","event":"scheduler.tick","claimed":3,"completed":3,"failed":0,"recovered":0,"skipped":false}
```

인터셉터가 아니라 미들웨어로 기록합니다 — 인터셉터는 라우트에 매칭된 요청에만 걸려 없는
경로의 `404` 가 안 남습니다. 미들웨어도 본문 파서보다 앞에 붙여야 파서가 거부한 요청(`413`,
깨진 JSON)까지 남습니다. 클라이언트가 끊은 요청은 `finish` 없이 `close` 만 오므로
`request.aborted` 로 남깁니다. `X-Request-Id` 는 영숫자·`.`·`_`·`-` 128자 이내일 때만
받습니다 — 줄바꿈이 섞이면 한 줄 = 한 JSON 이 깨집니다. 로거는 던지지 않습니다. 직렬화가
실패하는 값을 받으면 그 사실을 대신 기록합니다. 본문은 남기지 않습니다.

## 성능

파일 전체를 읽고 다시 쓰는 구조라 작업 수에 비례해 쓰기가 느려집니다. `npm run measure`.

## 한계

- **한 프로세스 안에서만 유효합니다.** 뮤텍스는 메모리 잠금이라 인스턴스를 여러 개 띄우면
  아무것도 막지 못합니다.
- **저장 중 프로세스가 죽으면 파일이 깨질 수 있습니다.** 파일 어댑터가 `'w'` 로 열어 먼저
  비우고 씁니다(소스 확인). 임시 파일 + `rename` 으로 막을 수 있는데 어댑터를 교체해야 해서
  하지 않았습니다. 확률은 낮지만 0 은 아닙니다.
- **쓰기가 실패하면 요청은 `500` 을 받고 메모리는 디스크로 되돌립니다.** `node-json-db` 는
  메모리를 먼저 바꾸고 파일에 쓰므로, 되돌리지 않으면 저장된 적 없는 작업이 다음 읽기에
  보입니다. 디스크도 못 읽는 경우는 되돌릴 기준이 없어 그대로 둡니다.
- **읽을 때마다 전체를 복사합니다.** 참조를 끊는 대가이고 위 측정치에 포함되어 있습니다.
- **멱등 키가 무한히 쌓입니다.** 만료가 없고, 매 요청 다른 키를 보내면 파일이 계속 커집니다.
- 파일을 바깥에서 고치면 반영되지 않습니다(첫 읽기 이후 메모리). 깨진 JSON 이나 모양이
  다른 파일이면 덮어쓰지 않고 기동을 멈춥니다 — 없거나 빈 파일만 새로 시작합니다.
- 인증·요청 수 제한 없음.

## 되돌린 결정

- **vitest 4 → 5.** CLI 가 깔아 준 `vitest@4` 에서 `npm install` 자체가 실패했습니다
  (`Cannot read properties of null (reading 'edgesOut')`, Node 22 의 npm 10). 하나씩 지워
  `vitest@4` 단독 재현을 확인하고 5 로 올렸습니다. `package-lock.json` 을 넣었습니다.
  처음엔 제 코드 문제인 줄 알고 엉뚱한 데를 봤습니다.
- **라이브러리가 "안전하지 않다" → "임계 구역이 좁다".** 소스를 읽고 바뀌었습니다. 코드는
  거의 같지만 왜 필요한지가 달라졌습니다.
- **인터셉터 → 미들웨어.** 없는 경로의 `404` 가 안 남는 것을 보고.
- **409 → 412.** `If-Match` 로 구현한 이상 RFC 대로.
- **음성 대조군을 다시 만듦.** 처음 것은 잠금 없는 쓰기를 테스트 안에서 따로 흉내 낸
  것이라 제 가드가 빠지면 깨지는지를 보지 않았습니다. 실제 뮤텍스를 끄고 같은 워크로드를
  돌리는 방식으로 바꿨고, 그러다 멱등 키 테스트가 잠금 없이도 통과하는 것을 알았습니다.
- **`null` 과 "같은 값" 을 놓침.** `@IsOptional` 은 `null` 도 생략으로 보고 검증을 건너뛰어
  `title: null` 이 저장되고 이후 제목 검색이 죽었습니다. 같은 상태를 다시 보내면 전이 검사
  없이 버전이 올랐습니다. 생략만 허용하고 `null` 은 거부하도록, 결과가 같으면 쓰지 않도록
  고쳤습니다. 규칙을 세워 놓고 코드 끝까지 밀어붙이지 못한 유형이었습니다.
- **`running` 표시의 설명을 고침.** 코드는 맞고 설명이 틀린 상태였습니다.
- **직접 정한 것.** 주기 10초·5건, `PATCH` 는 세 필드만, 자동 재시도 없음, `DELETE` 없음
  (넣는다면 삭제보다 `canceled` 상태가 이력이 남아 낫다고 봅니다).
  `@nestjs/schedule` 은 `@Interval` 데코레이터 대신 `SchedulerRegistry` 로 씁니다 — 데코레이터
  인자는 상수라 주기를 환경변수로 받으려면 실행 시점에 등록해야 합니다.
- **주기 실패가 프로세스를 죽이던 것.** 인터벌 콜백이 `runOnce()` 의 거부를 받지 않아, 디스크
  쓰기 오류 한 번에 unhandled rejection 으로 서버 전체가 내려갔습니다. 파일을 읽기 전용으로
  바꿔 주입해 보니 `tick_failed` 를 남기고 바로 종료했고 API 도 같이 죽었습니다. 콜백에서
  받도록 고쳤고(기록은 그대로 남습니다), 저장소가 던지게 만들어 살아남는지 보는 테스트를
  넣었습니다. 파일 권한 주입 자체는 테스트가 아니라 손으로 확인했습니다.
  "로거는 던지지 않는다"고 적어 놓고 정작 처리기가 던지는 것을 놓쳤습니다.

## 시간이 더 있다면

1. **저장 원자성.** 임시 파일 + `rename`. 단일 프로세스에서 데이터를 잃을 수 있는 유일한 항목.
2. **멱등 키 만료.**
3. **부분 쓰기.** 파일 전체 대신 경로 지정 쓰기로 위 측정치의 기울기를 낮추기.
4. **HTTP 끝단 처리량 측정.** 지금 잰 건 저장소 계층뿐입니다.
5. **여러 프로세스.** 조건부 쓰기가 있는 저장소로 옮기고 뮤텍스를 걷어내기. 바꿀 곳은
   `JobsRepository` 하나 — 모든 접근을 거기로 모아 둔 이유입니다.
